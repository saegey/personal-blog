When I first built [Monopad.app](https://monopad.app) — a race journal platform where athletes could upload activity files and generate rich posts — GPX felt like the obvious choice. It was open, human-readable XML, and popularized by platforms like Mapbox and Strava. FIT, by contrast, looked like Garmin's walled garden: binary blobs with little open-source tooling.

GPX looked friendly. FIT looked “off-limits.”

But as Monopad scaled, I ran into the limits of GPX the hard way. Long races (100+ miles) pushed file sizes into the tens of megabytes. Processing them in AWS Lambda was crushingly slow — ballooning uploads, sluggish XML parsing, and painful cold starts.

Switching to Go and FIT was like swapping SOAP for Protobuf: leaner, faster, purpose-built.

This post is part history lesson, part engineering case study — and a glimpse into where I'm going next.

A few years later, scaling my platform forced me to rethink everything. Processing GPX files for long races (100+ miles) through AWS Lambda and Node.js was crushingly slow — ballooning file sizes, sluggish parsing, and painful cold starts. The pivot to Go and FIT was like swapping SOAP for Protobuf: leaner, faster, purpose-built.

This post is both a history lesson and an engineering case study. Let's start at the beginning.

## A Brief History: GPX and FIT

### GPX (GPS Exchange Format)

- **Origin**: Created in 2002 by [TopoGrafix](https://www.topografix.com/gpx.asp) as an open XML schema for GPS waypoints, routes, and tracks.
- **Adoption**: Became the _de facto_ standard for route sharing, embraced by OpenStreetMap, Strava, Mapbox.
- **Strengths**: Open, human-readable, easy to hack.
- **Weaknesses**: Verbose, large, no unified schema for fitness metrics. Extensions abound, but they fragment the ecosystem.

### FIT (Flexible & Interoperable Data Transfer)

- **Origin**: Developed by Garmin in 2007 as a compact binary format for fitness devices.
- **Adoption**: Backbone of Garmin Connect, TrainingPeaks, Zwift, Wahoo, and more. Docs and SDKs live at [Garmin's developer site](https://developer.garmin.com/fit/protocol/).
- **Strengths**: Small, fast, extensible, designed for time-series activity data (power, HR, cadence, device info).
- **Weaknesses**: Binary (harder to hand-edit), historically seen as proprietary.

## Engineering Lessons from Monopad.app

The original pipeline looked like this:

- **Frontend**: Notion-style editor (Gatsby → React).
- **Backend**: AWS Amplify + DynamoDB + S3 + Lambdas triggered on file upload.
- **Flow**: Upload GPX → parse → aggregate → store metrics.

### Where GPX Broke Down

1. **File Size**: A 10MB GPX vs ~1.5MB FIT for the same ride. Uploads were 7× heavier.
2. **Parsing Overhead**: XML parsing in Node.js added hundreds of milliseconds before any real work.
3. **Cold Starts**: Lambda + Node.js + GPX = marathon in hiking boots.

### The Pivot to Go + FIT

Rewriting the parser in Go and switching to FIT flipped the experience:

- Cold starts became negligible.
- Parsing time dropped from ~257ms (GPX) to ~17ms (FIT).
- File size shrank 7×, making uploads painless.

The analogy holds:

- GPX is like XML — human-readable, verbose, text-based.
- FIT is like Protobuf — compact, binary, schema-based.

Readable isn't always usable at scale.

## Benchmarks on AWS Lambda

One thing I noticed early: local benchmarks can be misleading. My dev box (an M4 Pro Mac mini) made GPX parsing look tolerable. But in production, everything runs on AWS Lambda — and Lambda cores are slower, memory-bound, and often cold-started. To make the benchmarks realistic, I reran them directly in Lambda with 1024MB of memory provisioned.

I used the Serverless Framework to deploy a simple function that: 1. Loaded either a GPX or FIT file from S3. 2. Parsed it 50 times in memory. 3. Logged timing metrics for mean, p50, and p95 latencies.

The results were clear:

- FIT remained compact and fast even in the constrained Lambda environment.
- GPX ballooned in size and parse time, amplifying the cold-start penalty.
- The performance gap that looked big on my desktop was even larger in the cloud.

This reinforced a painful but valuable lesson:

- Your local machine ≠ production hardware.
- On Lambda, GPX parsing felt like riding a loaded touring bike uphill.
- FIT parsing felt like a race bike — efficient, tuned for the task.

It also underlined the economics: unless you’re willing to pay for bigger Lambda configs (and higher bills), you need a leaner format. FIT saves both milliseconds and dollars.

## The fit-analysis CLI

To make parsing reusable, I built a CLI: **fit-analysis**.  
Monopad consumed JSON, while other projects (like this blog) reuse the same binary.

Example output (simplified for brevity):

```bash
$ processFitFile --ftp 280 --fit ./BWR_San_Diego.fit
{
  "ElevationGain": 3512.7,
  "NormalizedPower": 188.7,
  "PowerZones": [...],
  "SimplifiedCoordinates": [...]
}
```

This decoupling makes it easy to plug FIT analysis into blogs, APIs, or future products.

## Looking Forward

Monopad.app is still online, but I've started sunsetting it in favor of something simpler:

- Drag-and-drop FIT upload → instant metrics + summaries.
- Public API → share and query activity data.
- AI Assistant → ask questions like “What was my average power on the final climb?”.
- Smarter compression → using algorithms like _Ramer–Douglas–Peucker_ to simplify GPS traces without losing fidelity.

The JSON output is still big (every second adds up with multiple sensors), but these experiments point toward a leaner product that could support both my blog and other developers.

## Conclusion

GPX isn't “bad.” It shines for sharing routes and staying human-readable. But for data-rich, performance-sensitive applications, FIT is the clear winner.

Building Monopad taught me that lesson the hard way. Hopefully, this post saves you the detour.
