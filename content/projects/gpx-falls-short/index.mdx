When I first built my race journal site in Gatsby, GPX felt like the obvious
choice. It was open, human-readable XML, and popularized by platforms like
Mapbox and Strava. FIT, on the other hand, seemed like Garmin's walled garden —
binary blobs without much open-source tooling. GPX looked friendly, FIT looked
“off-limits.”

A few years later, scaling my platform forced me to rethink everything. Processing GPX files for long races (100+ miles) through AWS Lambda and Node.js was crushingly slow — ballooning file sizes, sluggish parsing, and painful cold starts. The pivot to Go and FIT was like swapping SOAP for Protobuf: leaner, faster, purpose-built.

This post is both a history lesson and an engineering case study. Let's start at the beginning.

## A Brief History: GPX and FIT

### GPX (GPS Exchange Format)

- **Origin**: Created in **2002** by [TopoGrafix](https://www.topografix.com/gpx.asp), GPX was designed as an open XML schema for exchanging GPS waypoints, routes, and tracks across platforms.
- **Adoption**: By the mid-2000s, GPX became the _de facto_ lightweight standard for route sharing, embraced by mapping platforms, OpenStreetMap, Strava, and others.
- **Strengths**: Open, human-readable, easy to hack or hand-edit.
- **Weaknesses**: Verbose, large file sizes, no unified schema for advanced fitness data. Vendors tack on custom “extensions,” leading to fragmentation.

### FIT (Flexible & Interoperable Data Transfer)

- **Origin**: Developed by **Garmin in 2007** as a compact binary format for fitness devices.
- **Adoption**: FIT is now the backbone of Garmin Connect and supported by TrainingPeaks, Zwift, Wahoo, and countless others. Documentation and SDKs are published on [Garmin's developer site](https://developer.garmin.com/fit/protocol/).
- **Strengths**: Small, fast to parse, extensible, designed for time-series activity data (power, HR, cadence, laps, device info).
- **Weaknesses**: Binary (harder to hand-edit), historically seen as proprietary (though tooling has improved).

## The Engineering Journey: Learning the Hard Way

When I extended my blog into a platform, users could upload activity files and generate rich race/ride posts. The stack looked like this:

- **Frontend**: Notion-style post editor (Gatsby → React).
- **Backend**: AWS Amplify, DynamoDB, S3, and Lambda functions triggered on file upload.
- **Pipeline**: Upload → S3 → Lambda → parse GPX → aggregate metrics → write to DB.

### The Problems

1. **File Size**: Long races produced GPX files >10MB. FIT equivalents were ~1.5MB. Upload + download to Lambda containers was 7× heavier.
2. **Parsing Overhead**: XML parsing in Node.js was slow. Processing could take hundreds of ms just to load.
3. **Cold Starts**: Node.js Lambdas were sluggish (hundreds of ms). Combined with GPX size, this killed responsiveness.
4. **Scaling Pain**: Processing GPX felt like trying to run a marathon in hiking boots.

### The Pivot

I rewrote the parser in **Go**, switched to **FIT** files, and suddenly everything clicked:

- Cold starts dropped to near-instant.
- Parsing went from **~257ms → ~17ms**.
- File size shrank by 7×.
- Uploads finished quickly, even for 100+ mile rides.

The analogy is clear:  
**GPX is SOAP. FIT is Protobuf.**  
Human-readable isn't always human-usable at scale.

- **ns/op** → average nanoseconds per operation.
- **MB/s** → throughput (higher is better).
- **B/op** → average bytes allocated per operation.
- **allocs/op** → number of allocations per operation.

This shows how FIT dominates on speed and memory efficiency.

### Python Cross-Check

```python
import time, io, statistics, fitdecode, gpxpy

def parse_fit(data):
    with fitdecode.FitReader(io.BytesIO(data)) as fr:
        for _ in fr: pass

def parse_gpx(data):
    gpx = gpxpy.parse(io.BytesIO(data))
    for t in gpx.tracks:
        for s in t.segments:
            for _ in s.points: pass

def bench(label, func, data, n=25):
    times = []
    for _ in range(n):
        t0 = time.perf_counter()
        func(data)
        times.append((time.perf_counter() - t0) * 1000)
    print(f"{label}: mean={statistics.mean(times):.2f}ms p50={statistics.median(times):.2f}ms")

fit_bytes = open("testdata/activity.fit","rb").read()
gpx_bytes = open("testdata/activity.gpx","rb").read()

bench("FIT", parse_fit, fit_bytes)
bench("GPX", parse_gpx, gpx_bytes)
```

**Takeaway:** In Node, FIT parsing was **~2.3× faster** despite being the smaller binary format. This aligns with the **Go results** (FIT ~15× faster) and reinforces that the **format advantage** persists across runtimes; the magnitude depends on library + runtime overhead. (The **Python** cross‑check is a counter‑example driven by library implementation costs, not the underlying formats.)

**Node benchmark code (bench.js)**

```js
const fs = require('fs')
const { performance } = require('perf_hooks')
const FitParser =
  require('fit-file-parser').default || require('fit-file-parser')
const { XMLParser } = require('fast-xml-parser')

function stats(times) {
  const a = times.slice().sort((x, y) => x - y)
  const mean = a.reduce((s, x) => s + x, 0) / a.length
  const p50 = a[Math.floor(a.length * 0.5)]
  const p95 = a[Math.max(0, Math.floor(a.length * 0.95) - 1)]
  return { mean, p50, p95, min: a[0], max: a[a.length - 1], n: a.length }
}

function flatFindTrkpts(node, hits) {
  if (!node || typeof node !== 'object') return
  if (node.trkpt) {
    const pts = Array.isArray(node.trkpt) ? node.trkpt : [node.trkpt]
    for (const p of pts) hits.push(p)
  }
  for (const k of Object.keys(node)) {
    const v = node[k]
    if (Array.isArray(v)) v.forEach(x => flatFindTrkpts(x, hits))
    else if (typeof v === 'object') flatFindTrkpts(v, hits)
  }
}

function parseGpxCountPoints(xmlBuf) {
  const parser = new XMLParser({
    ignoreAttributes: false,
    attributeNamePrefix: '@_',
    trimValues: true,
  })
  const doc = parser.parse(xmlBuf.toString('utf8'))
  const hits = []
  flatFindTrkpts(doc, hits)
  let c = 0
  for (const pt of hits) {
    const _lat = pt['@_lat']
    const _lon = pt['@_lon']
    const _ele = pt.ele
    const _time = pt.time
    void _lat
    void _lon
    void _ele
    void _time
    c++
  }
  return c
}

function parseFitCountRecords(fitBuf, { force = true, speed = 'fast' } = {}) {
  return new Promise((resolve, reject) => {
    const parser = new (
      FitParser.constructor === Function ? FitParser : FitParser.default
    )({ force, speed })
    parser.parse(fitBuf, (err, data) => {
      if (err) return reject(err)
      const recs = Array.isArray(data.records) ? data.records : []
      let c = 0
      for (const r of recs) {
        const _lat = r.position_lat
        const _lon = r.position_long
        const _ele = r.altitude
        const _ts = r.timestamp
        void _lat
        void _lon
        void _ele
        void _ts
        c++
      }
      resolve(c)
    })
  })
}

async function bench(label, n, fn) {
  const times = []
  for (let i = 0; i < n; i++) {
    const t0 = performance.now()
    await fn()
    times.push(performance.now() - t0)
  }
  const s = stats(times)
  console.log(
    `${label}: n=${s.n} mean=${s.mean.toFixed(2)}ms p50=${s.p50.toFixed(2)}ms p95=${s.p95.toFixed(2)}ms min=${s.min.toFixed(2)}ms max=${s.max.toFixed(2)}ms`,
  )
  return s
}

async function main() {
  const fitPath = process.argv[2] || 'testdata/activity.fit'
  const gpxPath = process.argv[3] || 'testdata/activity.gpx'
  const N = Number(process.argv[4] || 25)
  const fitBuf = fs.readFileSync(fitPath)
  const gpxBuf = fs.readFileSync(gpxPath)
  console.log(
    `Sizes: FIT=${fitBuf.length.toLocaleString()} B  GPX=${gpxBuf.length.toLocaleString()} B`,
  )
  const gpxCount = parseGpxCountPoints(gpxBuf)
  const fitCount = await parseFitCountRecords(fitBuf)
  console.log(
    `Record/point counts: fit_records=${fitCount}  gpx_points=${gpxCount}`,
  )
  const fitStats = await bench('FIT (fit-file-parser)', N, async () => {
    await parseFitCountRecords(fitBuf)
  })
  const gpxStats = await bench('GPX (fast-xml-parser)', N, async () => {
    parseGpxCountPoints(gpxBuf)
  })
  console.log(
    `\nSpeedup (GPX/FIT mean): ${(gpxStats.mean / fitStats.mean).toFixed(2)}x`,
  )
  console.log(
    `File size ratio (GPX/FIT): ${(gpxBuf.length / fitBuf.length).toFixed(2)}x`,
  )
}

main().catch(e => {
  console.error(e)
  process.exit(1)
})
```

## Lessons Learned

- GPX is great for routes but a poor choice for activity tracking at scale.
- FIT is smaller, faster, richer, and extensible.
- Due diligence matters: I could've saved months if I'd researched FIT tooling earlier.

## What's Next

This work isn't just a postmortem. I'm working toward a new product direction:

- Drag-and-drop FIT upload → instant metrics + summaries.
- Public API → share and query your activities.
- AI Assistant → ask questions like “What was my average power in the final climb?” or auto-generate a race recap.
- Eventually: an MCP server for fitness data, so developers can plug it into their own apps.

GPX helped me start. FIT will help me scale.

## Conclusion

GPX isn't “bad” — it's just not built for what modern fitness platforms demand.  
It shines as a simple, open way to share tracks. But for data-rich, performance-sensitive applications, FIT is the clear winner.

I learned this the hard way. Hopefully, you won't have to.
